# docs-site — the molen.dev documentation site

A [VitePress](https://vitepress.dev) site that assembles the public documentation set. Almost
none of it is written here: the pages are **generated from the shipped build** so they cannot
drift from the engine.

```sh
pnpm docs:site:dev       # generate, then serve with hot reload
pnpm docs:site:build     # generate, then build to .vitepress/dist
pnpm docs:site:preview   # serve the built output
pnpm docs:site:check     # CI: fail if the generated navigation is stale
```

Each of those runs `pnpm -r build` first — the generators read packages' built `dist/`, per the
repo's build invariant, and the build stages the examples' `dist/` output.

## Where each section comes from

| Section | Source of truth | Generator |
|---|---|---|
| `/api/*` | `packages/*/dist/*.d.mts` — the files npm ships, one per `exports` entry | `scripts/generate-api.mjs` (TypeDoc) |
| `/reference/cli`, `/reference/mcp` | `OPS_CATALOG` in `packages/tooling/src/ops/describe.ts` | `scripts/generate-cli.mjs` |
| `/guide/*`, `/schemas/*`, `/llms.txt` | `docs-src/` (which for schemas is itself generated by `pnpm docs:gen`) | `scripts/generate-guides.mjs` |
| `/samples/*` | `examples/*` — package manifests, scene manifests, preview images | `scripts/generate-samples.mjs` |
| `/play/`, `/play/<id>/` | `examples/home/dist` (the gallery) and `examples/<id>/dist` — each example's own production build | `scripts/stage-hosted.mjs` (copies) |
| `/packs/index.json` + zips | `content/<pack>/` — one `molen/pack@1` zip per pack, in a `molen/pack-index@1` index | `scripts/stage-hosted.mjs` (`buildPack`) |
| Sidebar and nav | everything above | `scripts/generate-all.mjs` |

`/play/` and `/packs/` are not VitePress pages. After `vitepress build`, the `build` script runs
`scripts/stage-hosted.mjs`, which copies every example's `dist/` into `.vitepress/dist/play/` (the
gallery at `/play/`, each sample at `/play/<id>/`) and builds every `content/` pack into
`.vitepress/dist/packs/`, so a user who installed from npm can play the samples and run
`molen pack fetch https://molen.dev/packs/index.json` without cloning the repository. The script
builds nothing itself: each example is a devDependency of this package, which makes
`pnpm -r build` build them first. The step fails, and nothing is published, if an example under
`examples/` is not listed there, if its `dist/` is missing, if its HTML uses root-absolute asset
URLs (each example's Vite config sets `base: './'` so one build plays from any directory), or if a
lazily loaded chunk imports the entry chunk — with the samples' top-level `await mountExperience`
that deadlocks in every browser with a WebGPU adapter, so their Vite configs give three.js and the
client a chunk of their own.
`.vitepress/config.mts` gives root-relative markdown links to `/play/` and `/packs/` a `target`, so
the client router does not treat them as its own routes.

`scripts/packages.mjs` holds the shared package/entry-point manifest, read from each package's
`exports` map. **Adding a subpath export, a package, an op, a guide or a sample needs no edit
here** — regenerate and it appears in the pages and the sidebar. The one exception: a new example
must be added to this package's `devDependencies` to be published under `/play/`, and the build
fails until it is.

## What IS hand-written

- `index.md` — the landing page.
- `.vitepress/config.mts` — site framing; its `sidebar` is imported from generated JSON.
- `.vitepress/theme/custom.css` — brand tokens.
- The editorial arrays: `SAMPLES` and `KINDS` in `generate-samples.mjs` (what a sample is *for*),
  `GROUPS` in `generate-cli.mjs` (how commands are grouped), `GUIDE_ORDER` in
  `generate-guides.mjs` (learning order). Each generator warns on stdout when something on disk
  has no editorial entry yet, so gaps surface instead of silently disappearing.

## Committed vs generated

Generated pages are **gitignored** — they are build output, regenerated from source on every
build. The one committed artifact is `.vitepress/generated-nav.json`, because
`.vitepress/config.mts` imports it; `pnpm docs:site:check` fails if it is stale.

## Publishing to GitHub Pages

The manual `Release` workflow on `main` builds this site from the shipped docs and package
declarations. It builds again after semantic-release stamps a new package version, then uploads
`.vitepress/dist/` and deploys it to the `github-pages` environment after the package release
and metadata commit succeed. A run with only `docs:` commits does not publish npm packages, but
still deploys the refreshed site. Generated pages stay out of Git; the deployed artifact includes
them, sample previews, `/llms.txt`, the playable samples under `/play/` and the content packs
under `/packs/`.

In repository **Settings → Pages**, set **Source** to **GitHub Actions** and add `molen.dev` as the
**Custom domain**. Configure the apex DNS records with the domain provider using GitHub's current
Pages instructions, then enable HTTPS when GitHub offers it. This site uses root-relative routes
for `molen.dev`; configure that domain before expecting navigation at the temporary
`bendyline.github.io/molen/` address to work. GitHub Actions deployments do not need a `CNAME`
file; GitHub stores the custom-domain setting separately.

Sample pages are written for someone who installed from npm: each one links to the hosted build
(`PLAY_BASE`), offers `molen new --template <id>` when the tooling build ships that sample as a
template (read from `packages/tooling/dist/templates/index.json`), and links its source on GitHub
(`SOURCE_BASE`). None of them tells the reader to clone this repository.
